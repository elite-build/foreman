# Maintenance controls

`main` is protected by the repository ruleset **Protect main**, configured on GitHub rather than in this repository. Every change reaches `main` through a pull request with one approval from someone with write access, which is currently only the owner. A new push dismisses earlier approvals, and the most recent push must be approved by someone other than its pusher. Force-pushes and deleting `main` are blocked. Repository admins may bypass the review requirement when merging a pull request, but cannot push to `main` directly: GitHub does not let authors approve their own PRs, so without the bypass the owner's PRs, and PRs agents open with the owner's account, could never merge. Anything using the owner's credentials can use that bypass, so agents must not merge unless asked. No CODEOWNERS file is supplied; with a single writer it adds nothing. Add one and require code-owner review in the ruleset before granting anyone else write access.

The owner made the repository public on 2026-10-26. Publication did not complete the outstanding provenance, dependency licensing, security and platform checks. The project's original code uses Apache License 2.0; third-party material retains its separate terms. See [LICENSE](../LICENSE), [NOTICE](../NOTICE) and the [workspace names attribution](workspace-names.md). Selecting a project license does not complete the dependency/source-rights review.

No CI workflow is configured: the GitHub Actions workflow and Dependabot configuration were removed on 2026-10-26 to start again from scratch. Nothing runs automatically on pull requests or pushes, so run the checks locally before asking for review.

Two workflows exist, and both run only when someone starts them. **Installers** (`.github/workflows/installers.yml`) runs when someone with write access starts it from the Actions tab or with `gh workflow run installers.yml --ref <branch>`. It checks nothing; it packages the chosen ref with the `dist:mac:adhoc` and `dist:win` scripts (`dist:mac` when **sign-macos** is set): an Apple Silicon DMG on `macos-15` and an x64 NSIS installer on `windows-2022`. It uses a read-only token, SHA-pinned actions (checkout, setup-node, upload-artifact), a checkout without persisted credentials and a lifecycle-disabled install. It then rebuilds node-pty and runs `scripts/postinstall.mjs`, which restores the execute bit node-pty's macOS prebuilds omit from `spawn-helper` (without it every terminal in the packaged app fails with `posix_spawnp failed`). Each installer is uploaded as a run artifact that expires after 7 days. Started by hand it is not a release: there is no publishing step and, unless **sign-macos** is set (`gh workflow run installers.yml --ref <branch> -f sign-macos=true`), no signing identity or notarization, so macOS Gatekeeper and Windows SmartScreen warn about the installers. With **sign-macos**, as the Release workflow runs it, the macOS app is Developer ID signed and notarized instead (see [macOS signing and notarization](#macos-signing-and-notarization)); the Windows installer is unsigned either way. The unsigned macOS app is ad-hoc signed (`dist:mac:adhoc` overrides `build.mac` with `identity: "-"`, Hardened Runtime and notarization off): without that, Electron's linker signature is left broken once the bundle is assembled and a downloaded copy is killed at launch with no way to allow it. With it, a first launch is blocked once and then allowed with **Open Anyway** in System Settings → Privacy & Security (or `xattr -dr com.apple.quarantine /Applications/Foreman.app`). On this public repository, anyone signed in to GitHub can download a run's artifacts until they expire. Installer redistribution has not been cleared (see [dependency licenses](dependency-licenses.md#installer-and-bundle-distribution)), so treat these builds as internal test builds. **Release** (`.github/workflows/release.yml`) calls Installers for a version tag and attaches the installers to a draft release; see [Releases](#releases).

Gitleaks scans the checked-out source and reachable Git history with redacted output. Its exceptions match only specific synthetic fixture secrets, never an entire test directory. npm audit rejects high/critical dependency advisories, and license checks reject unreviewed licenses or changed package evidence. The source dependency inventory uses exact-version, integrity-bound reviews and retained notices; it does not clear installer redistribution. Run `npm run check:licenses:distribution` for the separate distribution findings, documented in [dependency licenses](dependency-licenses.md). These tools do not certify IPC, local CLI permissions, authentication, webviews, mobile access, sandbox execution or source provenance.

One dependency override answers an audit finding: `package.json` pins `@vercel/oidc` to 3.2.0 for `@vercel/sandbox` only. Every `@vercel/oidc` from 3.6.0 depends on `@vercel/cli-config`, and every `@vercel/cli-config` release through 0.3.3 pins `zod` 4.1.11 and bundles it into its entry point, which is affected by [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) (fixed in 4.6.6). Because the copy is bundled, overriding `zod` would only hide it from `npm audit`. `@vercel/sandbox` 3.6.1, the downgrade `npm audit fix --force` suggests, would avoid the chain but predates the command stdin API that `vercelProvider.ts` uses (3.7.0). `@vercel/sandbox` 3.9.0 imports only `getVercelOidcToken({ team, project, expirationBufferMs })` from `@vercel/oidc`, the same calls 3.6.1 made against 3.2.0. Foreman passes an access token with team and project explicitly, so the SDK never asks `@vercel/oidc` for credentials. The tradeoff: if an OIDC token (a JWT) is passed and it expires, 3.2.0 refreshes only from the Vercel CLI's file-stored login, not a keychain-stored one, and the SDK then keeps the expired token. `tests/vercelSdk.test.ts` checks the SDK still finds every OIDC function it imports and still sends Foreman's token. Remove the override once a `@vercel/sandbox` release resolves to a `@vercel/cli-config` built with zod 4.6.6 or later ([vercel/vercel#17678](https://github.com/vercel/vercel/issues/17678)), and check it again whenever `@vercel/sandbox` changes.

Do not mask a failing check to obtain a green result. Investigate installation, network and tool errors as failures. Human review remains necessary: a PR can change the guard or tests that produce its own check results. The repository guard checks source policy; it does not require a code owner or branch-protection rules.

Still to verify now that the repository is public: **Report a vulnerability** appears to a non-maintainer; no self-hosted runner, release credential or privileged workflow can run untrusted code (the Release workflow's one write-token job checks nothing out and runs no repository code; the Apple signing secrets reach only the signed macOS build, which runs the chosen ref's code, see [macOS signing and notarization](#macos-signing-and-notarization)); log/artifact retention and spending limits are approved before a new workflow is added. Security add-ons and settings are not enabled by committing these files.

### Releases

A release is a version in `package.json`, an annotated `v<version>` tag on a commit of `main`, and a GitHub release for that tag. `npm run release` (`scripts/release.mjs`, Node built-ins and Git only) does the first two; the manual **Release** workflow does the third. Versions follow [semver](https://semver.org/); a version with a suffix such as `0.2.0-beta.1` becomes a GitHub prerelease. The packaged app reports the `package.json` version (`app.getVersion()`).

1. **Bump the version on a branch.** `npm run release -- prepare <patch|minor|major|x.y.z>` sets the version in `package.json` and `package-lock.json` and changes nothing else. It refuses a dirty tree, `main`, and a version that doesn't come after the current one. Commit it (`git commit -am "Release <version>"`), run the local checks above, and merge the bump through a pull request: `main` accepts nothing else.
2. **Tag the merged version.** `npm run release -- tag --push` fetches `origin/main`, reads its version, refuses one that is already tagged or would come before the newest existing tag, then tags `origin/main` as `v<version>` and pushes the tag. It tags whatever version `origin/main` has: tag each bump as soon as it merges, because a version superseded by a later bump before it was tagged gets no tag. Without `--push` it only creates the tag locally and prints the push command; running it again with `--push` pushes that tag. It never moves or deletes a tag: if a tag is wrong, delete it by hand (`git push origin :refs/tags/v<version>` and `git tag -d v<version>`) before anyone relies on it.
3. **Build the draft release.** `gh workflow run release.yml --ref v<version>` (or **Actions → Release → Run workflow** with the tag selected). It fails unless it runs on a tag that names `package.json`'s version and is on `main`. It builds both installers through Installers (read-only token) with **sign-macos**, so the macOS app is Developer ID signed, notarized and checked, or the run fails before any release exists (see [macOS signing and notarization](#macos-signing-and-notarization)), and then, in a job that holds `contents: write` but checks nothing out and runs no repository or dependency code, creates a **draft** release with notes generated from merged pull requests, the DMG, the NSIS installer, `SHA256SUMS.txt` and what installed copies update themselves from: `latest.yml` (Windows) and `latest-mac.yml` (macOS) with the macOS zip and the blockmaps. electron-builder writes those because `build.publish` names this repository; the dist scripts still pass `--publish never`, so it uploads nothing. Running it again for a tag that already has a release, draft or published, fails rather than adding another.
4. **Review, then decide.** A draft is visible only to people with write access. Publishing it is what installed copies see: within hours (at their next scheduled check, wake or start) they offer the new version in the sidebar with the release's notes (see [Updates](../README.md#updates)), whether or not installers are attached. Where a copy can install updates itself (Windows, and macOS once the app is Developer ID signed) and the release carries `latest.yml` / `latest-mac.yml` and the installers they name, it downloads and installs from them; without them it falls back to the release page. Drafts are never offered; prereleases only to copies on the Beta channel. Edit the notes, then publish from the release page or with `gh release edit v<version> --draft=false`. Publishing makes the attached installers public: installer redistribution is not cleared yet (see [dependency licenses](dependency-licenses.md#installer-and-bundle-distribution)), the Windows installer is unsigned, and [SECURITY.md](../SECURITY.md) asks for a verified private reporting channel before a public release. Until those are settled, delete the installer assets, the update files (`latest.yml`, `latest-mac.yml`, the zip and the blockmaps) and `SHA256SUMS.txt` from the draft (`gh release delete-asset v<version> <name>`) and publish a source-only release, or leave it as a draft. GitHub adds source archives for the tag to every release.

The tag is unprotected: anyone with write access (currently only the owner) can create, move or delete `v*` tags. Owner decision: add a tag ruleset restricting creation, update and deletion of `refs/tags/v*` before granting anyone else write access.

### macOS signing and notarization

Foreman is distributed outside the Mac App Store, so a release's macOS app is signed with a **Developer ID Application** certificate and notarized by Apple. `build.mac` in `package.json` does both through electron-builder:

- **Signing.** `type: "distribution"` with no `identity`: electron-builder imports the certificate in `CSC_LINK` into a temporary keychain and signs with its Developer ID Application identity, never a development certificate. `forceCodeSigning` makes a macOS build that finds none fail rather than produce an unsigned app (Windows and Linux builds are unaffected).
- **Hardened Runtime and entitlements.** Notarization requires the Hardened Runtime. Foreman's own executable gets `build/entitlements.mac.plist`: `cs.allow-jit` for V8 (also used by the CLI, dictation helper and Cursor worker, which run that executable as Node) and `device.audio-input` for dictation. Everything else Foreman signs (Electron's helpers and frameworks, node-pty's `spawn-helper`, the native modules) gets `build/entitlements.mac.inherit.plist`, which has only `cs.allow-jit` for the renderer. Add an entitlement only for something Foreman demonstrably does: each one widens what code running in Foreman's processes may do.
- **Agents' executables.** `signIgnore` leaves `claude`, `codex` (and its `codex-code-mode-host` and `rg`) and Cursor's `cursorsandbox` and `rg` with their vendors' own Developer ID signatures, Hardened Runtime and entitlements. Re-signing would give each the inherit file: too little for Claude Code's executable, or too much for every Electron helper if it were widened to suit. Native modules that load into Foreman's processes (`pty.node`, sherpa-onnx, Cursor's tree-sitter bindings) are re-signed with Foreman's certificate, because the Hardened Runtime loads only libraries signed by the same team. When a dependency adds an executable, check its signature (`codesign -dvv <file>`) and either add it to `signIgnore` or confirm it runs with the inherit entitlements.
- **Notarization.** With `notarize: true` and `APPLE_API_KEY` (the path to the `.p8` file), `APPLE_API_KEY_ID` and `APPLE_API_ISSUER` set, electron-builder submits the signed app with `notarytool`, waits for Apple's verdict, fails the build on a rejection (printing Apple's log) and staples the ticket to the app. The DMG and the update zip are then made from the stapled app, so it opens without a network check. Without those variables electron-builder only warns and skips notarization, so the workflow checks them itself. The DMG is not signed, notarized or stapled itself: stapling it afterwards would change the bytes `latest-mac.yml` and the blockmap record.

`npm run dist:mac` on a Mac signs with the Developer ID Application certificate in your login keychain (and fails without one); it notarizes only when the three `APPLE_API_*` variables are set. `npm run dist:mac:adhoc` makes the ad-hoc signed test build instead.

**Repository secrets** (Settings → Secrets and variables → Actions). Never commit the certificate, key or any of these values: `.gitignore` and `npm run check:repository` reject `*.p12` and `*.p8` files.

| Secret | Contents |
| --- | --- |
| `CSC_LINK` | The Developer ID Application certificate with its private key, exported from Keychain Access as `.p12`, Base64-encoded (`base64 -i cert.p12`) |
| `CSC_KEY_PASSWORD` | The `.p12` export password |
| `APPLE_API_KEY` | The App Store Connect API key file (`AuthKey_<id>.p8`), Base64-encoded |
| `APPLE_API_KEY_ID` | That key's ID |
| `APPLE_API_ISSUER` | The issuer ID shown with the key (App Store Connect → Users and Access → Integrations) |
| `APPLE_TEAM_ID` | The Apple team ID; the verification requires the app's signature to name it |

**In the workflow.** Releasing is unchanged (see [Releases](#releases)): merge the version bump, `npm run release -- tag --push`, then `gh workflow run release.yml --ref v<version>`. Release calls Installers with **sign-macos** and passes it the six secrets; only the macOS signing steps receive them, and the Windows build never does. Those steps check that all six are set and that `APPLE_API_KEY` decodes to a `.p8` key, write the key to the runner's temporary folder (removed after the build), run `npm run dist:mac`, then run `scripts/verify-mac-release.sh` on the results. A missing secret, a certificate that isn't found, a rejected or timed-out notarization or a failed check fails the run, and Release then creates no draft. To try signing before tagging, run `gh workflow run installers.yml --ref <branch> -f sign-macos=true`: it signs and notarizes that branch with the release certificate, so use it only on code you would release.

The secrets are in the environment of the signed build step, which runs the chosen ref's build scripts and its dependencies (installed from the lockfile with lifecycle scripts off). They are repository secrets, so any workflow on any branch could read them, and anyone with write access can have a build signed. Owner decision: move them into a GitHub environment that only `v*` tags may deploy to, and name it in the Installers job, before granting anyone else write access.

**A failed notarization.** The failed step's log shows `notarytool`'s output with the submission ID and Apple's log, which lists each file that failed and why (typically a binary without a Developer ID signature, secure timestamp or Hardened Runtime, such as an executable a dependency added). To read it again on a Mac, with the API key saved outside the repository:

```sh
xcrun notarytool history --key AuthKey_<key id>.p8 --key-id <key id> --issuer <issuer id>
xcrun notarytool info <submission id> --key AuthKey_<key id>.p8 --key-id <key id> --issuer <issuer id>
xcrun notarytool log <submission id> --key AuthKey_<key id>.p8 --key-id <key id> --issuer <issuer id> notary-log.json
```

**Verifying a build.** `scripts/verify-mac-release.sh <folder> <team id>` runs on a Mac against a folder holding the DMG and the zip, for example the run's artifact (`gh run download <run id> -n Foreman-macOS-arm64 -D check`). It runs `hdiutil verify` on the DMG and, for `Foreman.app` in the DMG and in the zip, `codesign --verify --deep --strict --verbose=2`, `codesign -dv --verbose=4` (Developer ID Application authority, team, Hardened Runtime, timestamp), a signature check of every Mach-O file inside (`--deep` doesn't reach code in `Contents/Resources`), `xcrun stapler validate`, and `spctl --assess --type execute --verbose=4`, which must report `source=Notarized Developer ID` (skipped with a warning where Gatekeeper assessments are disabled, as they may be on CI runners). Before publishing the first signed release, also install it on a Mac that has never run Foreman: download the DMG through a browser, drag Foreman to Applications and open it. It should open without a Gatekeeper warning, and a terminal, each agent, dictation (with its microphone prompt) and the `foreman` command should all work.
