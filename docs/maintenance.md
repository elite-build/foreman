# Maintenance controls

`main` is protected by the repository ruleset **Protect main**, configured on GitHub rather than in this repository. Every change reaches `main` through a pull request with one approval from someone with write access, which is currently only the owner. A new push dismisses earlier approvals, and the most recent push must be approved by someone other than its pusher. Force-pushes and deleting `main` are blocked. Repository admins may bypass the review requirement when merging a pull request, but cannot push to `main` directly: GitHub does not let authors approve their own PRs, so without the bypass the owner's PRs, and PRs agents open with the owner's account, could never merge. Anything using the owner's credentials can use that bypass, so agents must not merge unless asked. No CODEOWNERS file is supplied; with a single writer it adds nothing. Add one and require code-owner review in the ruleset before granting anyone else write access.

The owner made the repository public on 2026-10-26. Publication did not complete the outstanding provenance, dependency licensing, security and platform checks. The project's original code uses Apache License 2.0; third-party material retains its separate terms. See [LICENSE](../LICENSE), [NOTICE](../NOTICE) and the [workspace names attribution](workspace-names.md). Selecting a project license does not complete the dependency/source-rights review.

**CI** (`.github/workflows/ci.yml`) runs on a pull request into `main` once it is ready for review. A draft runs nothing; marking it ready starts a run, each later push runs it again and cancels the run before it, and adding or removing a label runs it again for the new-component check. **Types and design system** runs `npm run typecheck`, `npm run check:ui`, `npm run check:workflows` and `scripts/check-new-components.mjs` against the PR's base with its labels, on `ubuntu-24.04`. `check:workflows` (`scripts/check-workflows.mjs`) checks the workflows themselves: every workflow sets top-level `permissions`, every action is pinned to a full commit SHA with its version in a comment, nothing uses `pull_request_target`, no job a pull request starts gets a secret or an environment (nor does a reusable workflow it calls, except behind an `if:`), and the required check names below are still the names of CI's jobs. It then runs actionlint, a release pinned by checksum in `scripts/security-tools.json`, with shellcheck over each `run:` script where shellcheck is installed, as it is on GitHub's Ubuntu runners. `tests/workflowPolicy.test.ts` runs the same rules in `npm test`. **Tests and build** runs `npm test -- --maxWorkers=4` and `npm run build` on `windows-2022`. Both use Node 24, a read-only token, SHA-pinned checkout and setup-node, a checkout without persisted credentials and a lifecycle-disabled install. The required check names are `Types and design system` and `Tests and build`. The **Require CI** ruleset requires both by name and has no bypass, so a failing PR can't be merged, not even by an admin; a draft's skipped jobs report success, which matters only because GitHub never merges a draft. Nothing runs after a merge. Outside contributors' PRs wait for approval before CI runs (see the table below).

**Nightly** (`.github/workflows/nightly.yml`) runs on `main` at 21:30 UTC and from the Actions tab: tests and build on `macos-15` with Node 24 and on `windows-2022` with Node 22, and on `ubuntu-24.04` `check:security`, `npm audit --audit-level=high`, `check:repository` and `check:licenses`. Nothing waits on it; a red run is fixed in the next PR. The Dependabot configuration removed on 2026-10-26 has not been restored.

Two more workflows run only when someone starts them. **Installers** (`.github/workflows/installers.yml`) runs when someone with write access starts it from the Actions tab or with `gh workflow run installers.yml --ref <branch>`, and when Release or Release dry run calls it. It packages the chosen ref with the `dist:mac:adhoc` and `dist:win` scripts (`dist:mac` when **sign-macos** is set): an Apple Silicon DMG on `macos-15` and an x64 NSIS installer on `windows-2022`. It uses a read-only token (plus `actions: read`, which SignPath needs to fetch an artifact), SHA-pinned actions (checkout, setup-node, upload-artifact, download-artifact, and SignPath's submit-signing-request for a signed Windows build), a checkout without persisted credentials and a lifecycle-disabled install. It then rebuilds node-pty and runs `scripts/postinstall.mjs`, which restores the execute bit node-pty's macOS prebuilds omit from `spawn-helper` (without it every terminal in the packaged app fails with `posix_spawnp failed`). Once each installer is built (and, when signed, verified), `scripts/smoke-packaged.mjs` starts it the way a user would get it: on macOS it copies `Foreman.app` out of the DMG, on Windows it installs the NSIS installer silently for the current user into a temporary folder. It starts the app with `--headless` and a fresh, empty `FOREMAN_DATA_DIR`, and fails the job unless, within three minutes, the app is still running, has created `foreman.db` (a SQLite file) and `cli.token` in that folder, answers `app-info` on its command-line socket (the named pipe on Windows) as the packaged build of `package.json`'s version using that folder, and refuses an admin-tier request (`settings-set`) that carries no token or a wrong one while letting the same request past the token check with the right one (where it then fails for its empty parameters, changing nothing). It then stops the app and uninstalls it. `--headless` opens no window, but Electron still needs the desktop session GitHub's macOS and Windows runners have, so it is not run elsewhere; `tests/smokePackaged.test.ts` checks its parts against the real CLI server. Each installer is uploaded as a run artifact that expires after 7 days. Started by hand it is not a release: there is no publishing step and, unless **sign-macos** is set (`gh workflow run installers.yml --ref main -f sign-macos=true`), no signing identity or notarization, so macOS Gatekeeper and Windows SmartScreen warn about the installers. With **sign-macos**, as the Release workflow runs it, the macOS app is Developer ID signed and notarized instead (see [macOS signing and notarization](#macos-signing-and-notarization)). The Windows installer is unsigned unless **sign-windows** is set, which signs `Foreman.exe` and the installer through SignPath once SignPath Foundation has approved Foreman and the repository is set up for it (see [Windows signing](#windows-signing)). The unsigned macOS app is ad-hoc signed (`dist:mac:adhoc` overrides `build.mac` with `identity: "-"`, Hardened Runtime and notarization off): without that, Electron's linker signature is left broken once the bundle is assembled and a downloaded copy is killed at launch with no way to allow it. With it, a first launch is blocked once and then allowed with **Open Anyway** in System Settings → Privacy & Security (or `xattr -dr com.apple.quarantine /Applications/Foreman.app`). On this public repository, anyone signed in to GitHub can download a run's artifacts until they expire. Installer redistribution has not been cleared (see [dependency licenses](dependency-licenses.md#installer-and-bundle-distribution)), so treat these builds as internal test builds. **Release** (`.github/workflows/release.yml`) calls Installers for a version tag and attaches the installers to a draft release; see [Releases](#releases).

**Release dry run** (`.github/workflows/release-dry-run.yml`) runs that build end to end without keys and without publishing: Installers with signing off (so the macOS app is ad-hoc signed rather than Developer ID signed and notarized), the smoke test of both packaged apps, then the draft job's checks of the release files, their renaming and `SHA256SUMS.txt`, listed in the run's summary. It creates no release, tag or attestation. It runs on a pull request into `main`, once it is ready for review, that changes `package.json` (which holds electron-builder's configuration and the dist scripts), `build/`, `resources/cli/`, `.signpath/`, the release, packaging and verification scripts or the Installers, Release or Release dry run workflows; on `main` every Sunday at 22:00 UTC; and from the Actions tab. It is not a required check. A pull request it runs on starts macOS and Windows builds, which are free on GitHub's standard runners for a public repository.

Gitleaks scans the checked-out source and reachable Git history with redacted output. Its exceptions match only specific synthetic fixture secrets, never an entire test directory. npm audit rejects high/critical dependency advisories, and license checks reject unreviewed licenses or changed package evidence. The source dependency inventory uses exact-version, integrity-bound reviews and retained notices; it does not clear installer redistribution. Run `npm run check:licenses:distribution` for the separate distribution findings, documented in [dependency licenses](dependency-licenses.md). These tools do not certify IPC, local CLI permissions, authentication, webviews, mobile access, sandbox execution or source provenance.

One dependency override answers an audit finding: `package.json` pins `@vercel/oidc` to 3.2.0 for `@vercel/sandbox` only. Every `@vercel/oidc` from 3.6.0 depends on `@vercel/cli-config`, and every `@vercel/cli-config` release through 0.3.3 pins `zod` 4.1.11 and bundles it into its entry point, which is affected by [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) (fixed in 4.6.6). Because the copy is bundled, overriding `zod` would only hide it from `npm audit`. `@vercel/sandbox` 3.6.1, the downgrade `npm audit fix --force` suggests, would avoid the chain but predates the command stdin API that `vercelProvider.ts` uses (3.7.0). `@vercel/sandbox` 3.9.0 imports only `getVercelOidcToken({ team, project, expirationBufferMs })` from `@vercel/oidc`, the same calls 3.6.1 made against 3.2.0. Foreman passes an access token with team and project explicitly, so the SDK never asks `@vercel/oidc` for credentials. The tradeoff: if an OIDC token (a JWT) is passed and it expires, 3.2.0 refreshes only from the Vercel CLI's file-stored login, not a keychain-stored one, and the SDK then keeps the expired token. `tests/vercelSdk.test.ts` checks the SDK still finds every OIDC function it imports and still sends Foreman's token. Remove the override once a `@vercel/sandbox` release resolves to a `@vercel/cli-config` built with zod 4.6.6 or later ([vercel/vercel#17678](https://github.com/vercel/vercel/issues/17678)), and check it again whenever `@vercel/sandbox` changes.

Do not mask a failing check to obtain a green result. Investigate installation, network and tool errors as failures. Human review remains necessary: a PR can change the guard or tests that produce its own check results. The repository guard checks source policy; it does not require a code owner or branch-protection rules.

Still to verify now that the repository is public: **Report a vulnerability** appears to a non-maintainer; no self-hosted runner, release credential or privileged workflow can run untrusted code (the Release workflow's one write-token job checks nothing out and runs no repository code; the Apple signing secrets reach only the signed macOS build, which runs the chosen ref's code, see [macOS signing and notarization](#macos-signing-and-notarization); the SignPath token reaches only the two signing jobs of a signed Windows build, which run no repository code, see [Windows signing](#windows-signing); both are meant to be secrets of the `release` environment, see [Protecting keys and tags](#protecting-keys-and-tags)); log/artifact retention and spending limits are approved before a new workflow is added. Security add-ons and settings are not enabled by committing these files.

### Releases

A release is a version in `package.json`, an annotated `v<version>` tag on a commit of `main`, and a GitHub release for that tag. Each pull request carries a release note in its body, one line for each thing a user notices (see the [pull request template](../.github/pull_request_template.md)). At release time they are collected into `CHANGELOG.md` in the version bump's pull request, in the order a reader needs them: **Before you update**, **Security**, **Fixed**, **Added**, **Changed** and **Development**. That entry, without **Development**, replaces the notes step 3 below drafts from pull request titles (see [decisions](decisions.md)). The [create-release skill](../.claude/skills/create-release/SKILL.md) runs every step below, including that one, for an agent asked to cut a release. `npm run release` (`scripts/release.mjs`, Node built-ins and Git only) does the first two; the manual **Release** workflow does the third. Versions follow [semver](https://semver.org/); a version with a suffix such as `0.2.0-beta.1` becomes a GitHub prerelease. The packaged app reports the `package.json` version (`app.getVersion()`).

1. **Bump the version on a branch.** `npm run release -- prepare <patch|minor|major|x.y.z>` sets the version in `package.json` and `package-lock.json` and changes nothing else. It refuses a dirty tree, `main`, and a version that doesn't come after the current one. Commit it (`git commit -am "Release <version>"`), run the local checks above, and merge the bump through a pull request: `main` accepts nothing else.
2. **Tag the merged version.** `npm run release -- tag --push` fetches `origin/main`, reads its version, refuses one that is already tagged or would come before the newest existing tag, then tags `origin/main` as `v<version>` and pushes the tag. It tags whatever version `origin/main` has: tag each bump as soon as it merges, because a version superseded by a later bump before it was tagged gets no tag. Without `--push` it only creates the tag locally and prints the push command; running it again with `--push` pushes that tag. It never moves or deletes a tag: if a tag is wrong, delete it by hand (`git push origin :refs/tags/v<version>` and `git tag -d v<version>`) before anyone relies on it. Once the **Release tags: fixed** ruleset is on, GitHub refuses that push until an admin turns the ruleset off for it (the ruleset's history records that); turn it on again straight after. A tag whose release was published stays: make the next version instead.
3. **Build the draft release.** `gh workflow run release.yml --ref v<version>` (or **Actions → Release → Run workflow** with the tag selected). It fails unless it runs on a tag that names `package.json`'s version and is on `main`. It builds both installers through Installers (read-only token) with **sign-macos**, so the macOS app is Developer ID signed, notarized and checked, or the run fails before any release exists. The jobs that sign wait for a maintainer to approve them on the run's page, because they deploy to the `release` environment (see [Protecting keys and tags](#protecting-keys-and-tags)), and each installer is started once by the smoke test (see [macOS signing and notarization](#macos-signing-and-notarization)). When the repository variable `SIGNPATH_SIGNING` is `true`, it also passes **sign-windows**, so `Foreman.exe` and the Windows installer are signed through SignPath, each signing request waiting for an approver, and checked with SignTool, or again the run fails first (see [Windows signing](#windows-signing)); otherwise the Windows installer is unsigned and the run warns that it is. Then, in a job that holds `contents: write` but checks nothing out and runs no repository or dependency code, records a signed build provenance attestation for every file (see [Build provenance](#build-provenance)) and creates a **draft** release with notes generated from merged pull requests, the DMG, the NSIS installer, `SHA256SUMS.txt` and what installed copies update themselves from: `latest.yml` (Windows) and `latest-mac.yml` (macOS) with the macOS zip and the blockmaps. electron-builder writes those because `build.publish` names this repository; the dist scripts still pass `--publish never`, so it uploads nothing. Running it again for a tag that already has a release, draft or published, fails rather than adding another.
4. **Review, then decide.** A draft is visible only to people with write access. Publishing it is what installed copies see: within hours (at their next scheduled check, wake or start) they offer the new version in the sidebar with the release's notes (see [Updates](../README.md#updates)), whether or not installers are attached. Where a copy can install updates itself (Windows, and macOS once the app is Developer ID signed) and the release carries `latest.yml` / `latest-mac.yml` and the installers they name, it downloads and installs from them; without them it falls back to the release page. Drafts are never offered; prereleases only to copies on the Beta channel. Edit the notes, then publish from the release page or with `gh release edit v<version> --draft=false`. Publishing makes the attached installers public. Installers are cleared for distribution (owner decision, 2026-11-06), so keep every asset the workflow attached: the DMG, the NSIS installer, the update files (`latest.yml`, `latest-mac.yml`, the zip and the blockmaps) and `SHA256SUMS.txt`. Without them installed copies stop updating themselves. Until Windows signing is turned on, the Windows installer is unsigned, so SmartScreen warns on first run. GitHub adds source archives for the tag to every release.

Until the tag ruleset in [Protecting keys and tags](#protecting-keys-and-tags) is applied, the tag is unprotected: anyone with write access (currently only the owner) can create, move or delete `v*` tags.

### Protecting keys and tags

The workflows are ready for the settings below; applying them is a GitHub settings change for the owner, made on GitHub and read back afterwards, never by an agent. Until they are applied, the signing secrets are repository secrets (any workflow on any branch could read them; Release still reaches them through `secrets: inherit`, so releases keep working in the meantime) and `v*` tags are unprotected. Create the environment before the next signed run: a run that names an environment that doesn't exist yet creates it with no protection at all. Apply them in this order.

**1. A `release` environment** (Settings → Environments → New environment, name `release`):

- **Required reviewers:** the owner. Leave **Prevent self-review** off while the owner is the only maintainer, or nobody could approve the owner's own runs. Turn it on once someone else can review.
- **Allow administrators to bypass configured protection rules:** off.
- **Deployment branches and tags:** **Selected branches and tags**, with the branch rule `main` and the tag rule `v*`.
- **Environment secrets:** `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`, `APPLE_TEAM_ID` (see [macOS signing and notarization](#macos-signing-and-notarization)), and `SIGNPATH_API_TOKEN` once SignPath has issued it. Add each to the environment with its current value, then delete the repository secret of the same name (Settings → Secrets and variables → Actions). The SignPath repository variables are identifiers, not secrets, and stay where they are.

The same with the GitHub CLI, as the owner (`<owner id>` from `gh api users/<owner login> --jq .id`):

```sh
gh api -X PUT repos/elite-build/foreman/environments/release --input - <<'EOF'
{"wait_timer": 0, "prevent_self_review": false, "can_admins_bypass": false,
 "reviewers": [{"type": "User", "id": <owner id>}],
 "deployment_branch_policy": {"protected_branches": false, "custom_branch_policies": true}}
EOF
gh api -X POST repos/elite-build/foreman/environments/release/deployment-branch-policies -f name=main -f type=branch
gh api -X POST repos/elite-build/foreman/environments/release/deployment-branch-policies -f name='v*' -f type=tag
gh secret set CSC_LINK --env release < <file holding the value>    # and each of the others
gh secret delete CSC_LINK                                         # the repository secret, once the environment has it
```

Every job that signs names this environment: **Package / macOS (signed)**, **Sign / Foreman.exe** and **Sign / Windows installer** in Installers. Each waits on the run's page until a reviewer approves it (jobs waiting at the same time can be approved together), runs only for `main` or a `v*` tag, and is the only job that can read the secrets. Release dry run and pull requests never reach them: their runs leave signing off, and a pull request's ref isn't `main` or a `v*` tag. `npm run check:workflows` fails a pull-request workflow that names an environment or a secret.

**2. Two tag rulesets** (Settings → Rules → Rulesets → New ruleset → New tag ruleset), both **Active** and targeting the tag pattern `v*`:

- **Release tags: creation** restricts creations, with the **Repository admin** role in its bypass list (**Always**). The release path, `npm run release -- tag --push` run by a maintainer, is then the only way a `v*` tag appears; nobody else with write access can push one, and no workflow creates tags (`gh release create --verify-tag` requires the tag to exist).
- **Release tags: fixed** restricts updates and deletions and blocks force pushes, with an **empty** bypass list, so nobody moves or deletes a release tag. It is a separate ruleset because a bypass applies to every rule of the ruleset it is in.

```sh
gh api -X POST repos/elite-build/foreman/rulesets --input - <<'EOF'
{"name": "Release tags: creation", "target": "tag", "enforcement": "active",
 "conditions": {"ref_name": {"include": ["refs/tags/v*"], "exclude": []}},
 "rules": [{"type": "creation"}],
 "bypass_actors": [{"actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "always"}]}
EOF
gh api -X POST repos/elite-build/foreman/rulesets --input - <<'EOF'
{"name": "Release tags: fixed", "target": "tag", "enforcement": "active",
 "conditions": {"ref_name": {"include": ["refs/tags/v*"], "exclude": []}},
 "rules": [{"type": "update"}, {"type": "deletion"}, {"type": "non_fast_forward"}],
 "bypass_actors": []}
EOF
gh api repos/elite-build/foreman/rulesets --jq '.[] | [.id, .name, .target, .enforcement] | @tsv'
```

(`actor_id` 5 is GitHub's built-in admin repository role.) Then check them: pushing a `v*` tag from an account with write access but not admin is refused, and `git push origin :refs/tags/v<existing>` is refused for everyone.

**3. Immutable releases** (Settings → General → Releases → **Enable release immutability**, or `gh api -X PUT repos/elite-build/foreman/immutable-releases`). A published release's assets can then no longer be added, replaced or deleted and its tag can't be moved or deleted; its title and notes stay editable. It applies to releases published after it is turned on. Drafts stay editable, which the release steps rely on: every asset is attached while the release is a draft, and step 4 only edits notes and publishes. GitHub also attests each immutable release, which `gh release verify v<version>` and `gh release verify-asset v<version> <file>` check.

**Why the tag still comes first.** Creating the tag only when the release is published would mean building from a commit of `main` rather than from the tag, and changing `npm run release -- tag`, the Release workflow's tag checks and the create-release skill. The tag-first flow builds exactly the tagged commit, and with the rulesets and immutable releases above the tag can't change once pushed, nor the release once published. A tag whose build failed stays unpublished, and the fix ships as the next version, as step 2 of [Releases](#releases) already says.

### Build provenance

The Release workflow's draft job records a signed [build provenance attestation](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds) for every file it attaches: the DMG, the macOS zip, the Windows installer, the blockmaps, `latest.yml`, `latest-mac.yml` and `SHA256SUMS.txt`, under the names they are published with. `actions/attest-build-provenance` (SHA-pinned) signs a statement of each file's SHA-256 with a short-lived Sigstore certificate issued to that workflow run, naming the repository, the workflow file, the tag and the commit, and stores it with the repository's attestations. The job has only the `id-token: write` and `attestations: write` it needs for that, beside the `contents: write` that creates the draft. Release dry run makes no attestation.

Anyone can check a download with the GitHub CLI, signed in to any GitHub account:

```sh
gh attestation verify Foreman-1.2.15-arm64.dmg --repo elite-build/foreman
gh attestation verify Foreman-Setup-1.2.15.exe --repo elite-build/foreman --signer-workflow elite-build/foreman/.github/workflows/release.yml
```

It passes only for a file whose bytes this repository's Release workflow attested, and prints the run's tag and commit. An attestation says where a file was built; it doesn't replace the code signatures ([code signing policy](../CODE_SIGNING.md)), and a file it fails for should not be installed.

### A bad release

How installed copies find a release (`src/shared/appUpdate.ts`, `src/main/updates.ts`, `src/main/updateInstaller.ts`): a few seconds after each start, when the computer wakes and on their schedule (every 4 hours by default, hourly or daily if chosen), copies on the **Stable** channel ask `api.github.com/repos/elite-build/foreman/releases/latest`, the published release GitHub marks **Latest**, and offer it when its version is newer than theirs. Copies on **Beta** take the newest version among the 20 most recent releases, prereleases and full releases alike, drafts never. To download, electron-updater reads the update feed (`latest.yml` / `latest-mac.yml`) of the release GitHub reports, and the download fails unless that names the version offered. When a later check no longer finds the offered version, the offer is withdrawn: a download in progress stops and an install-at-quit is cancelled. On macOS, an update Squirrel has already staged still installs at the next quit. No copy is ever offered an older version (`allowDowngrade` is off, and only a newer version counts).

To stop a bad release `v<bad>` reaching more users:

1. **Mark the last good release as latest.** `gh release edit v<good> --latest`, then check `gh api repos/elite-build/foreman/releases/latest --jq .tag_name` prints `v<good>`. Stable copies that haven't updated stop being offered `v<bad>` at their next check, within their check interval. Immutability locks a release's assets and tag; if GitHub ever refuses the change, publishing the fix (step 4) is what remains.
2. **Beta copies** still see `v<bad>` as the newest version, whether it is a prerelease or not. They stop only when a newer version is published, or when `v<bad>` is no longer published (`gh release edit v<bad> --draft=true`, which GitHub may refuse for an immutable release). Go to step 4.
3. **Say so in its notes.** Edit `v<bad>`'s notes to begin with what is wrong and what to do (`gh release edit v<bad> --notes-file <file>`, UTF-8 without a BOM); notes stay editable on an immutable release. Don't delete its assets or tag: installed copies of `v<bad>` and anyone verifying a download still read them, and the tag rulesets and immutability refuse it anyway.
4. **Ship the fix as the next version.** Copies that already installed `v<bad>` are reached only by a newer version. Make a patch release from `main` with the fix or a revert (step 1 of [Releases](#releases)), publish it as usual, and check it is **Latest**. Its notes say under **Before you update** what `v<bad>` did and whether users need to do anything.
5. **Users who already updated** and can't wait can reinstall `v<good>` from its release page, but only if `v<bad>` changed nothing in the database: an older Foreman refuses a `foreman.db` from a newer schema (`foreman.db is from a newer version of Foreman`). Check with `git diff v<good> v<bad> -- src/main/db.ts`. If it added a migration, tell them to wait for the fix, or to restore a backup taken before the update (Settings → Data & devices).
6. A release that exposes users' data or credentials is also a security advisory: follow [SECURITY.md](../SECURITY.md).

### Windows signing

Windows releases are to be Authenticode signed through [SignPath Foundation](https://signpath.org)'s free programme for open-source projects. Foreman's application is pending, so signing is off and the Windows installer is unsigned. The [code signing policy](../CODE_SIGNING.md) holds the policy SignPath Foundation asks for: what is signed, the team's roles, privacy, how to verify a download, and the setup that turns signing on.

In the workflows, Installers' **sign-windows** input does the signing, and Release passes it when the repository variable `SIGNPATH_SIGNING` is `true`. The Windows job builds the app with `electron-builder --win dir` and uploads `Foreman.exe` as a run artifact. `signpath/github-action-submit-signing-request` (SHA-pinned) asks SignPath to sign it; SignPath fetches the artifact from GitHub itself and waits for an approver. The job then checks the signed file, puts it back into `dist/win-unpacked`, builds the NSIS installer from that folder with `--prepackaged` (electron-builder doesn't touch the executable again), and has the installer signed the same way. Signing changes the installer's bytes, so `scripts/windows-update-feed.mjs` then recomputes `latest.yml` and the blockmap with electron-builder's own code, or installed copies would reject the update. `scripts/verify-windows-release.ps1` checks `Foreman.exe`, the installer, the `Foreman.exe` inside the installer and `latest.yml` before the artifact is uploaded. The token is used only in the two jobs that submit the signing requests (**Sign / Foreman.exe** and **Sign / Windows installer**), which deploy to the `release` environment, check nothing out and run no repository or dependency code: they hand SignPath an artifact of the run and upload what comes back. Building the app, building the installer from the signed `Foreman.exe` (the unpacked app travels between the jobs as a one-day artifact, `windows-unpacked`), recomputing the update feed, verifying and the smoke test run in jobs without it. The checks are SignTool's `verify /pa`, a SHA-256 digest, the signer `SignPath Foundation`, an RFC 3161 timestamp and the same certificate on both files. A missing setting, a rejected or timed-out request, or a failed check fails the job, and Release then creates no draft. The intermediate artifacts are named `unsigned-windows-*`, never `Foreman-*`, because the draft-release job attaches every `Foreman-*` artifact.

The SignPath settings are one secret, `SIGNPATH_API_TOKEN`, which belongs in the `release` environment (see [Protecting keys and tags](#protecting-keys-and-tags)), and the repository variables listed in [Turning signing on](../CODE_SIGNING.md#turning-signing-on). Only the two signing jobs receive the token. The SignPath artifact configurations are kept for review in `.signpath/artifact-configurations/`. A signed Windows build therefore waits for four approvals: each signing job's deployment to `release` on GitHub, and each signing request in SignPath.

### macOS signing and notarization

Foreman is distributed outside the Mac App Store, so a release's macOS app is signed with a **Developer ID Application** certificate and notarized by Apple. `build.mac` in `package.json` does both through electron-builder:

- **Signing.** `type: "distribution"` with no `identity`: electron-builder imports the certificate in `CSC_LINK` into a temporary keychain and signs with its Developer ID Application identity, never a development certificate. `forceCodeSigning` makes a macOS build that finds none fail rather than produce an unsigned app (Windows and Linux builds are unaffected).
- **Hardened Runtime and entitlements.** Notarization requires the Hardened Runtime. Foreman's own executable gets `build/entitlements.mac.plist`: `cs.allow-jit` for V8 (also used by the CLI, dictation helper and Cursor worker, which run that executable as Node) and `device.audio-input` for dictation. Everything else Foreman signs (Electron's helpers and frameworks, node-pty's `spawn-helper`, the native modules) gets `build/entitlements.mac.inherit.plist`, which has only `cs.allow-jit` for the renderer. Add an entitlement only for something Foreman demonstrably does: each one widens what code running in Foreman's processes may do.
- **Agents' executables.** `signIgnore` leaves `claude`, `codex` (and its `codex-code-mode-host` and `rg`) and Cursor's `cursorsandbox` and `rg` with their vendors' own Developer ID signatures, Hardened Runtime and entitlements. Re-signing would give each the inherit file: too little for Claude Code's executable, or too much for every Electron helper if it were widened to suit. Native modules that load into Foreman's processes (`pty.node`, sherpa-onnx, Cursor's tree-sitter bindings) are re-signed with Foreman's certificate, because the Hardened Runtime loads only libraries signed by the same team. When a dependency adds an executable, check its signature (`codesign -dvv <file>`) and either add it to `signIgnore` or confirm it runs with the inherit entitlements.
- **Notarization.** With `notarize: true` and `APPLE_API_KEY` (the path to the `.p8` file), `APPLE_API_KEY_ID` and `APPLE_API_ISSUER` set, electron-builder submits the signed app with `notarytool`, waits for Apple's verdict, fails the build on a rejection (printing Apple's log) and staples the ticket to the app. The DMG and the update zip are then made from the stapled app, so it opens without a network check. Without those variables electron-builder only warns and skips notarization, so the workflow checks them itself. The DMG is not signed, notarized or stapled itself: stapling it afterwards would change the bytes `latest-mac.yml` and the blockmap record.

`npm run dist:mac` on a Mac signs with the Developer ID Application certificate in your login keychain (and fails without one); it notarizes only when the three `APPLE_API_*` variables are set. `npm run dist:mac:adhoc` makes the ad-hoc signed test build instead.

**Secrets of the `release` environment** (Settings → Environments → release → Environment secrets; see [Protecting keys and tags](#protecting-keys-and-tags)). Never commit the certificate, key or any of these values: `.gitignore` and `npm run check:repository` reject `*.p12` and `*.p8` files.

| Secret | Contents |
| --- | --- |
| `CSC_LINK` | The Developer ID Application certificate with its private key, exported from Keychain Access as `.p12`, Base64-encoded (`base64 -i cert.p12`) |
| `CSC_KEY_PASSWORD` | The `.p12` export password |
| `APPLE_API_KEY` | The App Store Connect API key file (`AuthKey_<id>.p8`), Base64-encoded |
| `APPLE_API_KEY_ID` | That key's ID |
| `APPLE_API_ISSUER` | The issuer ID shown with the key (App Store Connect → Users and Access → Integrations) |
| `APPLE_TEAM_ID` | The Apple team ID; the verification requires the app's signature to name it |

**In the workflow.** Releasing is unchanged (see [Releases](#releases)): merge the version bump, `npm run release -- tag --push`, then `gh workflow run release.yml --ref v<version>`. Release calls Installers with **sign-macos**; its **Package / macOS (signed)** job deploys to the `release` environment, waits for a maintainer's approval and reads the six secrets from it. No other job receives them. Those steps check that all six are set and that `APPLE_API_KEY` decodes to a `.p8` key, write the key to the runner's temporary folder (removed after the build), run `npm run dist:mac`, then run `scripts/verify-mac-release.sh` on the results. If the app is notarized but stapling its ticket fails (`Failed to staple your application`, usually a dropped connection to Apple's CloudKit ticket service, which `@electron/notarize` retries for only a few seconds), the step waits a minute and builds again, up to three attempts in all. `stapler validate` in the verification calls the same service, so the script tries it up to five times when it can't connect, and fails at once on a missing or invalid ticket. A missing secret, a certificate that isn't found, a rejected or timed-out notarization or a failed check fails the run, and Release then creates no draft. To try signing before tagging, run `gh workflow run installers.yml --ref main -f sign-macos=true`: it signs and notarizes `main` with the release certificate. The `release` environment admits only `main` and `v*` tags, so a run on another branch fails at that job; to sign a branch's build, add the branch to the environment's deployment rules for that run and remove it afterwards.

The secrets are in the environment of the signed build step, which runs the chosen ref's build scripts and its dependencies (installed from the lockfile with lifecycle scripts off): electron-builder signs and notarizes while it packages, so on macOS the build and the keys can't be in separate jobs. That job is the only one that names the `release` environment, so once the secrets are moved there (see [Protecting keys and tags](#protecting-keys-and-tags)) it runs only on `main` or a `v*` tag, and only after a maintainer approves it. While they are still repository secrets, any workflow on any branch could read them.

**A failed notarization.** The failed step's log shows `notarytool`'s output with the submission ID and Apple's log, which lists each file that failed and why (typically a binary without a Developer ID signature, secure timestamp or Hardened Runtime, such as an executable a dependency added). To read it again on a Mac, with the API key saved outside the repository:

```sh
xcrun notarytool history --key AuthKey_<key id>.p8 --key-id <key id> --issuer <issuer id>
xcrun notarytool info <submission id> --key AuthKey_<key id>.p8 --key-id <key id> --issuer <issuer id>
xcrun notarytool log <submission id> --key AuthKey_<key id>.p8 --key-id <key id> --issuer <issuer id> notary-log.json
```

**Verifying a build.** `scripts/verify-mac-release.sh <folder> <team id>` runs on a Mac against a folder holding the DMG and the zip, for example the run's artifact (`gh run download <run id> -n Foreman-macOS-arm64 -D check`). It runs `hdiutil verify` on the DMG and, for `Foreman.app` in the DMG and in the zip, `codesign --verify --deep --strict --verbose=2`, `codesign -dv --verbose=4` (Developer ID Application authority, team, Hardened Runtime, timestamp), a signature check of every Mach-O file inside (`--deep` doesn't reach code in `Contents/Resources`), `xcrun stapler validate`, and `spctl --assess --type execute --verbose=4`, which must report `source=Notarized Developer ID` (skipped with a warning where Gatekeeper assessments are disabled, as they may be on CI runners). Before publishing the first signed release, also install it on a Mac that has never run Foreman: download the DMG through a browser, drag Foreman to Applications and open it. It should open without a Gatekeeper warning, and a terminal, each agent, dictation (with its microphone prompt) and the `foreman` command should all work.
